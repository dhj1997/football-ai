# 结算遗漏与近期亏损复盘设计

日期：2026-09-20

## 目标

修复已结束比赛中“旧预测已有模拟下注、最新预测改为 `no_bet`”时下注长期保持 `placed` 的问题，并确保候选重新计算不会绕过预测生成阶段已经冻结的数据质量决策。基于修复后的真实结算链路复盘近期亏损，不通过篡改历史预测或立即调参掩盖问题。

## 已确认约束

- 继续自动模拟下注，不增加全局暂停或熔断。
- 不修改历史预测概率、赔率快照、下注金额或已结算赛果。
- 已结束比赛的开放下注按真实最终比分定向结算，结算接口必须保持幂等。
- 所有新增业务逻辑使用现有 MySQL/Repository 抽象；SQLite 只在测试中使用。

## 方案

### 1. 结算选择

`SettlementService.settle_fixture()` 继续结算每个模型的当前预测，以保持预测质量指标覆盖；同时读取当前比赛中状态为 `placed` 的模拟下注，并通过下注的 `prediction_id` 读取其不可变历史预测。将两组预测按 ID 去重后处理。

这样，新预测可以产生预测评价，旧预测可以完成它实际拥有的下注结算；没有开放下注的旧预测不会重新进入指标统计，避免重复计算历史版本。找不到关联预测时不猜测、不迁移下注，只记录跳过结果并保持现有数据。

### 2. 模拟下注执行闸门

在 `BankrollService` 的候选生成和最终执行两个边界都校验原始预测的冻结 `decision`：

- 必须存在 `decision.status == "bet"`；
- 任何阻断原因码 `stale_odds`、`odds_pending`、`no_matching_market`、`missing_player_data`、`ai_unavailable`、`low_confidence`、`implausible_market`、`risk_limit` 出现时都不得生成或执行候选；
- 继续使用现有 `build_candidates()` 的 Edge、EV、赔率新鲜度、数据完整度和资金风控检查；
- 模型原始 `model_recommendation` 的 `no_bet` 不单独否决，因为当前产品契约明确由后端确定性决策负责 Portfolio 资格。

最终执行边界再次检查，覆盖额外候选和未来调用方，避免只在一个入口校验而被其他路径绕过。被拦截的预测只保留原始决策和原因码，不写入下注记录。

### 3. 复盘输出

不在本次修复中调整模型权重或门槛。部署后重新运行结算，再按模型、市场、预测阶段和原因码读取指标；只有在修复后的样本量和数据质量足够时，才单独提出模型校准设计。现有小样本亏损只作为风险信号，不作为直接调参依据。

## 数据流与错误处理

1. 终场比赛进入结算任务。
2. 读取当前预测；追加该比赛所有开放 `placed` 下注对应的历史预测；按预测 ID 去重。
3. 为每条预测创建或校正评价记录；仅对 `placed` 下注调用原子 `settle_bet()`。
4. 结算异常按现有任务错误路径返回，不部分伪造成功；重复任务读取已有评价/已结算下注并返回相同财务结果。
5. 生产补结算只针对已结束比赛的开放下注，不触碰未开赛下注。

## 测试

- 结算回归：旧预测有 `placed` 下注、同模型新预测为 `no_bet` 时，旧下注被结算，新预测仍产生一次评价；重复运行不增加流水。
- 候选回归：冻结 `no_bet` 及每个阻断原因码均不能生成或执行候选；正常冻结 `bet` 且通过现有 Portfolio 门槛的预测仍可下注。
- 运行现有结算、资金、市场决策和 API 焦点测试；不运行与本改动无关的全量长测试。

## 部署与验证

提交并推送代码后，按现有生产部署流程构建、重启 API/Web，并验证服务状态、健康接口、指标接口和下注接口。确认诺丁汉森林 vs 考文垂下注从 `placed` 变为 `settled`，赛果为客胜对应的输注结果，且资金流水只写入一次。
