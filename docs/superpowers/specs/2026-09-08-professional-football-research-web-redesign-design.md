# 专业足球竞猜研究 Web 端重设计

## 背景

现有 Web 端已经覆盖赛程、比赛详情、球队、积分榜、模型表现和后台作业，但页面仍偏向功能模块堆叠，比赛筛选、证据核验和模型判断之间缺少稳定的研究顺序。

本设计面向专业竞猜研究者，将 Web 端重组为高密度、可追溯的足球研究终端。首页采用“赛程研究台”，单场详情采用“证据优先”结构。视觉设计可以脱离当前样式，但必须保留现有业务能力、API 契约和真实数据状态。

本规格覆盖并替代 `2026-09-06-single-match-research-workspace-design.md` 中与页面信息顺序、布局和视觉系统有关的内容；其预测权限等既有业务规则继续有效。`2026-09-08-fast-fixture-detail-two-source-design.md` 的快速读取与双数据源规则不变。

## 已确认方向

- 目标用户：专业竞猜研究者。
- 首页形态：赛程研究台。
- 首页密度：保持当前视觉稿的信息密度。
- 详情形态：证据优先。
- 业务数据源：仅 TheSportsDB 和懂球帝。
- 设计基调：克制、专业、可扫描，不采用博彩霓虹屏或营销落地页风格。

## 目标

1. 用户进入首页后能快速找到值得研究的比赛，并同时识别证据状态、模型共识和风险。
2. 用户进入详情页后先确认数据是否完整、来自哪里、何时更新，再阅读模型结论。
3. 缺少赔率、阵容或其他证据时页面保持可用，并明确说明该缺口是否参与当前判断。
4. 桌面端适合连续研究多场比赛，移动端保持相同的信息顺序和关键内容。
5. 页面请求继续优先使用本地已同步数据，不因重设计引入新的外部请求或加载等待。

## 非目标

- 不修改预测算法、模拟投注、结算、定时器和数据同步策略。
- 不增加新闻、社区、聊天、登录、付费或自动下注功能。
- 不新增数据源，不恢复 API-Football 或 ESPN 的业务调用。
- 不伪造赔率、首发、伤停、交锋或比赛事件。
- 不对后端或现有组件做与本次页面体验无关的重构。

## 信息架构

现有路由保持不变：

- `/`：赛程研究台，产品的主要入口。
- `/matches/[fixtureId]`：单场比赛证据与模型研究报告。
- `/standings`：积分榜。
- `/teams/[leagueKey]/[teamId]`：球队资料。
- `/performance`：模型复盘与资金表现。
- `/admin`：数据同步、模型设置和自动化作业。

首页和单场详情进行完整信息重组。积分榜、球队、模型复盘和后台管理保留现有功能结构，只统一全局导航、颜色、排版、表格、状态、按钮、空状态和响应式规则。

## 全局框架

### 顶部导航

深色顶部栏固定产品身份和一级入口：

- 品牌：`EDGE / FOOTBALL`，副标题为“足球竞猜研究终端”。
- 一级入口：赛程研究、机会雷达、模型复盘、资金管理。
- 当前尚无独立路由的入口映射到最接近的现有能力，不新增空页面：机会雷达进入带研究状态的赛程列表；资金管理进入现有表现与账户区域。
- 管理台作为次级入口，不与主要研究流程争夺视觉注意力。
- 右侧显示数据同步新鲜度或运行状态，不能仅用颜色表达。

顶部栏在移动端收敛为品牌、当前页面标题和菜单按钮。导航展开后覆盖显示，不挤压页面主体。

### 视觉系统

- 主背景使用低对比冷灰，内容面使用白色，顶部栏使用深青黑。
- 蓝色表示当前选择与中性分析，绿色表示证据就绪，琥珀色表示待确认，红色只表示高风险或失败。
- 页面分区使用连续布局、细边线和轻底色；卡片只用于独立重复项目，不使用卡片套卡片。
- 圆角不超过 6px，不使用渐变、装饰光斑或大面积单一蓝紫色。
- 字距固定为 `0`。数字概率、比分和赔率使用等宽数字特性，字号不随视口宽度缩放。
- 命令按钮使用 Lucide 图标；熟悉的返回、刷新、导出、设置操作优先采用图标并提供工具提示和可访问名称。

## 首页：赛程研究台

### 页面头部

页面头部只包含“赛程研究台”、当前日期范围和简短同步状态，不设置营销式大标题。日期切换为分段控件：昨日、今日、明日、未来 7 天。联赛筛选紧随其下，支持全部、英超、西甲、中超和足协杯。

### 桌面布局

主体为约 `3:2` 的左右工作区：

- 左侧是比赛列表，按时间和状态稳定排序。
- 右侧是当前选中比赛的快速研究摘要。
- 选择列表行只更新右侧摘要；“打开完整分析”进入详情页。
- 列表和摘要均使用固定列宽或最小宽度，状态文本变化不能引发布局跳动。

比赛行稳定展示：

- 开球时间或完场状态。
- 联赛。
- 主客队中文名称。
- 比分或 `VS`。
- 证据状态。
- 模型状态或共识。
- 风险等级或待复核原因。

快速研究摘要展示：比赛身份、综合方向、模型一致度、证据质量、胜平负概率、近期效率、伤停差异、市场状态和关键变量。它是筛选入口，不重复详情页的全部证据。

### 移动布局

移动端改为单列：日期与联赛筛选、比赛列表、选中比赛的抽屉式快速摘要。默认不在每一行展开完整摘要，避免长列表失去扫描效率。队名允许两行，比分区宽度固定。

## 详情页：证据优先

详情页使用一条从事实到判断的固定研究链。模型概率不能先于证据完整度出现。

### 1. 比赛头部

紧凑展示联赛、双方队徽与中文队名、开球时间或比分、比赛状态、场地、天气、数据更新时间和比赛 ID。头部高度应让下一段证据完整度在桌面首屏内可见。

### 2. 证据完整度

证据完整度是详情页第一主模块，固定检查以下六项：

1. 赛程与积分。
2. 近期赛果。
3. 伤停信息。
4. 预计或确认阵容。
5. 赛事情报。
6. 即时赔率。

每项显示就绪状态、来源和更新时间。来源只允许 TheSportsDB 或懂球帝；缺失项显示“待同步”及是否排除在当前结论之外。总览使用 `n / 6` 和文字状态，不能只显示进度条。

### 3. 近期状态

双方并列展示统一样本窗口下的场均积分、进球、失球和近期战绩。比较条用于快速阅读，原始数值必须同时可见。样本不足时直接显示样本数，不将小样本包装成稳定趋势。

### 4. 伤停与阵容

双方并列展示确认缺阵、出场存疑和预计主力完整度，并列出影响最大的已知球员。所有球员名称必须在 API 输出前经过 `to_chinese_player_name`，页面和日志不得直接显示供应商英文名。

首发未确认时显示预计阵容及状态；首发确认后替换为正式阵容，并保留同步时间。

### 5. 赔率与市场

有数据时展示 1X2、亚洲让球和更新时间；存在多个快照时再展示变化方向。没有赔率时显示明确空状态，并说明赔率未参与当前判断，不使用估算值补齐。

### 6. 模型综合判断

模型结论在所有证据模块之后展示，包括：

- 双模型各自概率和方向。
- 两个模型方向是否一致。
- 支持因素。
- 反对因素。
- 待确认项。
- 当前风险等级。

不存在模型结果时展示可生成状态，不伪造综合概率。模型结果存在分歧时分别展示，不生成虚假的单一共识。

### 研究侧栏

桌面端右侧设置窄研究侧栏，只显示证据阅读进度、当前风险、缺失提醒和研究操作。侧栏不提前展示模型结论。滚动时可保持可见，但不能遮挡页尾或移动端内容。

移动端将侧栏拆分：证据进度放在完整度模块后，风险和操作放在模型结论后，保持“先证据、后判断”的顺序。

## 次级页面

### 积分榜与球队资料

- 沿用研究终端外壳和高密度表格样式。
- 排名、赛次、胜平负、净胜球和积分列保持固定对齐。
- 球队页按赛季概况、近期比赛和阵容顺序展示，不增加内容门户模块。

### 模型复盘与资金管理

- 以真实收益、命中、样本量、回撤和模型归因为主。
- 小样本、仅影子运行和未结算状态必须使用明确文字。
- 不用单一绿色收益数字掩盖样本和风险条件。

### 管理台

- 保留同步、预测、模型配置和常驻作业能力。
- 使用更紧凑的操作表和状态日志，不套用面向普通用户的比赛卡片。
- 危险或会产生外部调用的操作继续提供明确反馈。

## 加载、错误与空状态

- 首页优先显示本地缓存列表，再后台刷新；刷新时保留现有内容并显示非阻塞状态。
- 详情页只读取本地数据库和已有缓存，不在页面请求中调用外部供应商或模型。
- 首次无缓存时使用与最终布局尺寸一致的骨架，不显示会造成整页位移的居中加载文案。
- 可选证据缺失时返回并展示已有内容，不把整页变成错误页。
- 详情主请求失败时展示重试操作；刷新失败但有旧数据时继续显示旧数据并标明更新时间。
- 空赔率、空交锋、未确认首发、单模型和无模型必须各有明确状态。

## 组件边界

不引入新 UI 框架。复用 Next.js、React 和现有 `lucide-react`。

建议组件边界：

- `ResearchShell`：全局品牌、导航和系统状态。
- `ResearchFilters`：日期与联赛筛选。
- `FixtureResearchList`：稳定列宽的比赛列表。
- `QuickResearchPanel`：首页选中比赛摘要。
- `MatchIdentityHeader`：详情比赛身份与状态。
- `EvidenceAudit`：六项证据完整度和来源。
- `FormComparison`：近期状态对照。
- `AvailabilityComparison`：伤停与阵容。
- `MarketEvidence`：赔率和变化。
- `ModelConclusion`：双模型结论与正反因素。
- `ResearchProgressRail`：详情研究进度和操作。

派生数据继续集中在无副作用函数中。只在现有文件体积或职责明显妨碍实现时拆分组件，不进行全站目录重构。

## 数据与行为约束

- 继续使用现有路由和 API 字段；纯视觉重组不要求后端新增字段。
- 页面请求不得直接调用 TheSportsDB 或懂球帝。
- 详情接口不得调用外部供应商、模型或写入证据。
- 预测权限保持：`scheduled` 和 `live` 可生成；`finished`、`postponed`、`cancelled` 不可生成。
- 首页缓存优先、后台刷新和 revision 失效逻辑继续保留。
- 用户或其他会话的现有未提交修改必须保留；实施只修改重设计所需文件。

## 响应式与可访问性

- 桌面重点验证 `1440 x 900` 和 `1280 x 800`。
- 移动端重点验证 `390 x 844` 和 `430 x 932`。
- 不允许横向页面滚动、文字与状态重叠或动态内容改变固定数据列尺寸。
- 所有交互元素可通过键盘访问，焦点状态清晰。
- 状态不能只靠颜色表达；图标按钮提供 `aria-label` 和工具提示。
- 尊重 `prefers-reduced-motion`，骨架和页面切换不使用持续动画。

## 测试与验收

### 最小自动化检查

- 首页日期和联赛筛选仍返回正确列表。
- 选中比赛后快速摘要与该比赛一致。
- 详情证据顺序固定，模型结论位于证据模块之后。
- 完场比赛不能生成预测，未开赛和进行中规则不变。
- 无赔率、无模型、部分证据和失败响应均有正确降级。
- `pnpm lint` 和 `pnpm build` 通过。

### 浏览器验收

- 使用真实本地 API 数据检查首页和单场详情，不只验证静态样例。
- 桌面和移动端分别截图检查首屏、完整长页和滚动状态。
- 检查长中文队名、超长联赛名、空字段和比分更新时无重叠。
- 验证首页缓存内容立即可见，后台刷新不会清空列表。
- 验证详情加载不再长时间停留在“加载数据”，且缺失证据不会阻塞整页。

## 实施范围

实施按以下顺序进行：

1. 建立全局视觉变量和研究终端外壳。
2. 重组首页赛程列表与快速研究摘要。
3. 重组单场详情为证据优先结构。
4. 将次级页面和管理台统一到新视觉系统。
5. 补充与改动风险匹配的前端测试，并完成真实数据浏览器验收。

本轮不修改后端业务逻辑。若实施中发现视觉稿所需字段当前不存在，优先使用现有字段或明确缺失状态，不扩展后端契约。
