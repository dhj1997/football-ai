# 双模型独立账户与首发重算下注设计

## 目标

修复“当前 AI 显示不下注，但模拟账户仍有旧下注”的版本错位，并允许在首发未确认时按正常规则下注。DeepSeek 与 GPT 各自预测、各自决策、各自维护模拟账户，互不占用余额、仓位或风险额度。

本设计只覆盖模拟下注，不连接真实投注平台。真实平台已经接受的下注不能由系统撤销，本设计中的“作废”仅表示模拟账本退款。

## 已选方案

采用“当前预测替换旧模拟单”：

1. 首发未确认不是绝对禁止下注条件。
2. AI 推荐下注且后端赔率、数据和风控校验通过时，按正常仓位下注，不应用首发未确认折扣。
3. 开球前产生新的当前预测时，旧预测对应的活动模拟单作废并全额退回本金。
4. 新预测通过校验则创建新单；新预测为 `no_bet` 或被后端否决时不补单。
5. 首发确认必须触发一次新预测，因此旧的未确认首发模拟单会被替换。
6. 开球后不再作废、退款或重新下注，已有活动单按赛果正常结算。

未采用以下方案：

- 保留旧单并补差额或对冲：会同时产生相反暴露，账目和页面难以解释。
- 新旧两单并存：会重复占用风险并再次造成预测与账户不一致。

## 决策架构

两个模型使用同一版本的 `PromptContract`、相同证据快照和相同 JSON Schema，但分别调用、分别存储和分别决策：

```text
相同比赛证据
  -> DeepSeek 预测 -> DeepSeek 市场校验 -> DeepSeek 风控 -> DeepSeek 模拟账户
  -> GPT 预测      -> GPT 市场校验      -> GPT 风控      -> GPT 模拟账户
```

模型间不存在共识门槛。一个模型的失败、`no_bet`、市场方向或账户余额不得影响另一个模型。

### AI 职责

每个模型独立输出：

- 胜、平、负概率和亚洲让球覆盖概率；
- 最可能赛果；
- `bet` 或 `no_bet` 推荐；
- 推荐市场、选择方向、置信度和中文理由；
- 首发未确认、球员数据缺失等不确定性说明。

AI 输出 `no_bet` 时，后端不得自行创建下注。AI 不输出最终仓位，也不能覆盖后端计算的赔率价值和风险限制。

### 后端职责

后端对 AI 的 `bet` 推荐执行确定性校验：

- 匹配当前可用市场和选择方向；
- 计算回本概率、去水概率和预期优势；
- 检查赔率新鲜度、数据完整性、置信度和账户风险；
- 使用现有正常仓位算法计算下注金额，保留单场最高 2% 和单日未结算风险上限；
- 输出标准原因码和最终 `bet`、`no_bet` 或 `insufficient_data`。

`lineup_unconfirmed` 从阻断原因改为警告和不确定性证据，不单独改变最终状态，也不降低仓位。负优势、赔率过期、无匹配市场、严重数据不足和风险超限仍可否决 AI 的下注推荐。此次改动不降低其他 `no_bet` 标准。

## 独立模拟账户

账本的隔离键为 `(competition_id, model_key)`。DeepSeek 与 GPT 各自拥有：

- 初始余额；
- 可用余额；
- 当日未结算风险；
- 活动下注；
- 结算记录和收益指标。

重复下注检查、单场上限和每日风险上限只能查询同一个 `model_key`，不能跨模型互相阻断。页面的模型标签页只读取该模型的预测、下注和收益。

现有共享模拟账本不能可靠拆分。迁移时清理旧共享下注、账单和结算数据，并为两个模型分别初始化同额账户。该操作不影响比赛、证据和当前预测数据。

## 当前预测与下注一致性

系统保持以下不变量：

1. 每个 `(fixture_id, model_key)` 最多只有一个当前预测。
2. 每个 `(fixture_id, model_key)` 最多只有一个活动模拟单。
3. 活动模拟单的 `prediction_id` 必须等于页面当前显示的预测 ID。
4. 当前预测的 AI 推荐不是 `bet` 时，不允许存在活动模拟单。
5. DeepSeek 的下注只能出现在 DeepSeek 账户，GPT 同理。

因此，手动预测、定时重算或首发确认重算只要成功产生新预测，就会在开球前替换旧活动单。首发确认不是唯一替换事件，但它是必须触发重算的事件。

## 模拟单生命周期

模拟单状态限定为：

- `placed`：当前活动单，等待结算或新预测替换；
- `superseded`：开球前被新预测替换，下注本金已全额退回；
- `settled`：比赛完成后已按结果结算。

模拟单记录下注时的 `lineup_confirmed`、预测阶段和模型标识。替换时记录 `superseded_at`、`superseded_reason` 和新预测 ID，原因统一为 `prediction_replaced`；首发确认场景额外记录触发阶段 `confirmed_lineup`。

### 原子替换流程

模型调用和响应校验在数据库事务外完成。新预测可持久化后，在同一数据库事务中：

1. 锁定该模型、该比赛的旧 `placed` 模拟单；
2. 将旧单改为 `superseded`；
3. 写入等于旧下注本金的退款流水；
4. 根据新预测的最终决定，选择不下注或扣款创建新单；
5. 更新该模型账户余额并提交事务。

任一步失败时整笔账务回滚，不能出现只退款未换单、只换单未退款或双活动单。新预测为 `no_bet` 时，事务只作废退款，不创建新单。

首发确认后即使某个模型调用失败，该模型的旧未确认首发模拟单也应在开球前作废退款，状态显示 AI 不可用且无新下注；另一个模型继续独立运行。

当前版本保留策略可以删除已替换的旧模拟单和对应净额为零的“下注加退款”流水，但必须成对删除，不能改变账户余额。

## 触发时机

- 手动预测：开球前成功生成新预测后替换该模型旧单。
- 定时预测：开球前成功生成新预测后替换该模型旧单。
- 首发确认：必须刷新证据并分别重新调用两个模型，然后各自替换旧单。
- 开球后：禁止创建、作废或替换赛前模拟单。
- 已结算单：永不作废或重新结算。

新单必须使用重算时的最新有效赔率，不能沿用旧单赔率。如果新赔率过期或不存在，旧单仍按当前版本规则作废退款，新决定为 `no_bet` 或 `insufficient_data`。

## API 与页面

每个模型标签页展示同一模型的：

- 当前预测和 AI 推荐；
- 后端赔率价值计算；
- 最终执行决定；
- 当前模拟单、独立余额和独立收益。

首发未确认时展示“首发未确认，公布后将重新分析”，但不显示为禁止下注。首发确认并完成重算后只展示当前版本，不保留旧账单列表。若新预测为 `no_bet`，页面不得继续展示旧活动单。

接口必须返回稳定的 `model_key`、当前 `prediction_id`、账户范围和模拟单状态，使前端无需猜测数据归属。所有用户可见文案使用简体中文。

## 失败处理

- 单个 AI 超时、空响应或 Schema 校验失败：该模型显示不可用，不影响另一模型。
- Poisson 基线可以继续展示，但不得代替失败的 AI 自动下注。
- 替换事务失败：保留事务前账务状态并返回明确错误，不能提交半成品。
- 重复任务并发：使用事务锁或唯一约束保证每模型每比赛只有一个活动单。
- 开球时间边界：以服务器标准化时间为准，进入开球时间后拒绝任何替换操作。

## 验收与测试

测试范围只覆盖本次高风险行为：

1. 首发未确认不再单独产生 `no_bet`，且不缩小正常仓位。
2. AI 推荐 `no_bet` 时后端不能创建下注。
3. AI 推荐 `bet` 且赔率价值、数据和风控通过时创建正常仓位下注。
4. DeepSeek 和 GPT 的余额、风险、下注和收益互不影响。
5. 同一模型开球前新预测会作废旧单、全额退款，并按新决定创建新单或保持无单。
6. 首发确认后旧未确认首发单必定作废；新决定 `no_bet` 时不补单。
7. 新旧模拟单不能同时处于 `placed`；事务失败不能产生余额偏差。
8. 开球后和已结算模拟单不能作废或替换。
9. 一个模型不可用时，另一个模型仍能完成预测和下注流程。
10. API 与页面当前预测、模型账户和活动模拟单的 `model_key`、`prediction_id` 完全一致。
11. 桌面和移动端验证两个模型标签页，不出现“AI 不下注但仍显示旧下注”。

完成后运行风险相称的单元测试、API 契约测试、前端 lint、TypeScript 检查和生产构建，并使用真实缓存比赛完成浏览器验证。

## 非目标

- 不连接真实投注平台。
- 不实现对冲、补差额或跨模型资金共享。
- 不因希望增加下注数量而降低正优势、赔率新鲜度、数据完整性或风险上限。
- 不保留旧版本下注和历史账单页面。
- 不进行与双模型账户、决策一致性和首发重算无关的架构重构。
